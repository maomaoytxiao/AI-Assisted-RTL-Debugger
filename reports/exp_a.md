- **Timestamp:** 126000 ps (1 ns after the rising edge at 125000 ps)
- **Cycle:** 13 (rising edges at 5, 15, ..., 125 ns)

## Analysis
In `fill`, the testbench pushes 8 entries. The DUT accepts 7 writes (wr_ptr 0000 to 0111). On the edge at 125000, `full` rises to 1 while count is only 7. Because `wr_fire = wr_en && !full`, wr_fire drops to 0 even though wr_en stays 1 until 140000. The 8th write (value 0x8) is dropped and `overflow` is raised. Every later failure follows from this. The FIFO holds one entry fewer than the model, so count is off by one, empty and underflow assert early, and rd_data stays at 0x7 because 0x8 was never stored. At 306000, with the pointers wrapped (wr_ptr=1110, rd_ptr=0111), full is again 1 at count 7. The bug is therefore systematic, not tied to one pointer position.

## Suspected root cause
`build/debug/exp_a/rtl/sync_fifo.sv:54-55`, signal **`full`**:
```verilog
assign full      = (wr_ptr[AW-1:0] + 1'b1 ==
                    rd_ptr[AW-1:0]);
```
This is the classic "one slot left" full test. It ignores the wrap bit and is true when the FIFO holds DEPTH-1 entries. The spec says `full` means the FIFO holds DEPTH entries. Given the extra-bit pointers, the expected form would be:
```verilog
assign full = (wr_ptr[AW] != rd_ptr[AW]) && (wr_ptr[AW-1:0] == rd_ptr[AW-1:0]);
```
(Equivalently `count == DEPTH`.)

## Alternatives considered
- **Stimulus/testbench problem:** rejected. wr_en is still 1 when the write is dropped.
- **Wrong count formula (line 56):** rejected. count tracks the accepted writes correctly.
- **Pointer increment bug (lines 68/71):** rejected. wr_ptr increments by 1 per accepted write.
- **Read path or rd_data bug:** rejected as the primary cause. The wrong rd_data is downstream, because 0x8 was never written.
