## Analysis
At 321000 the FIFO is correctly full: wr_ptr=0000 and rd_ptr=1000, so count=8, full=1 and overflow=1. The write should be dropped, and wr_fire=0 agrees. At the 325000 edge, wr_ptr still advances to 0001 while rd_ptr holds. That makes count 9 and clears full. With full now wrongly 0, wr_fire goes to 1, so the next two overflow writes are really stored. mem[1] holds the unread value 0x0a, and at 335000 it is overwritten with 0xE1. This explains the later `rd_data: got 0xe1 expected 0xa` error. wr_ptr stays ahead by the number of dropped writes, so count, empty and full stay off in the underflow, wraparound, simultaneous_rw and reset_mid_operation tests.

## Suspected root cause
`build/debug/exp_c/rtl/sync_fifo.sv:67` (signal `wr_ptr`):

```verilog
            if (wr_en)                      // line 67
                wr_ptr <= wr_ptr + 1'b1;    // line 68
```

The write pointer advances on the raw request `wr_en` instead of on the accepted write `wr_fire` (`wr_en && !full`). The memory write on line 78 correctly uses `wr_fire`, so the two sides disagree. Suggested fix: `if (wr_fire)`.

Alternatives I ruled out:
- **full equation (lines 54-55):** correct for the pointer values seen.
- **count subtraction (line 56):** matches the pointers.
- **Memory write enable (line 78):** uses `wr_fire`, so its misbehaviour is a side effect of the wrong full flag.
- **Read path:** rd_ptr is static in the window, and the fill and drain tests pass.
- **Testbench model:** matches the spec rule that writes while full are dropped.

## Confidence and limitations
